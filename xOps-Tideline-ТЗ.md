# xOps Tideline — техническое задание (итерация 1)

> **Название.** `xOps Tideline`. Tideline — линия прилива: граница, которая сдвигается сама и каждый раз оставляет новый рисунок. Метафора скользящего окна планирования.
> Запасные варианты, если занято: `xOps Slipstream`, `xOps Driftline`, `xOps Slotline`.
> Slug для Railway / домена: `tideline`.

---

## 1. Контекст и цель

Команда из 5–9 инженеров ведёт несколько параллельных проектов. Менеджменту нужна прозрачность двух вещей:

1. **Чем занят каждый инженер** в конкретные даты и на каком проекте.
2. **Кто и насколько свободен** в заданном интервале — чтобы ответить на вопрос «я хочу через две недели стартовать проект, хватит ли людей».

Сейчас это ведётся в таблице. Таблица решает задачу, но требует ручной работы при добавлении проектов, вставке строк, переносе недель и не даёт нормального поиска свободного ресурса.

Специфика планирования: горизонт короткий. **Скользящее окно в две недели** — на неделе N планируются недели N и N+1, на неделе N+1 неделя N+1 корректируется и добавляется N+2.

**Цель первой итерации:** заменить таблицу веб-сервисом, где ввод занимает меньше времени, чем в Google Sheets, а вопрос «кто свободен с 3 по 14 августа» решается одной формой, а не глазами.

---

## 2. Пользователи и сценарии

| Роль | Кто | Что делает |
|---|---|---|
| Редактор (итерация 1 — один) | тимлид | ведёт аллокации, проекты, закрывает недели |
| Наблюдатель | менеджмент, смежные команды | смотрит по read-only ссылке, ничего не меняет |

**Ключевые сценарии, по которым оценивать успех:**

- **S1.** Проставить загрузку на неделю всей команде — меньше двух минут, только с клавиатуры и мышью, без диалоговых окон.
- **S2.** Ответить на «хватит ли людей на проект в 15 чел-дней с 3 по 14 августа» — за один экран, с конкретными именами.
- **S3.** Закрыть неделю и сдвинуть окно — одна кнопка, с автоматическим снимком в историю.
- **S4.** Менеджер открывает ссылку и видит текущую картину без логина и без возможности что-то сломать.
- **S5.** Понять, где план разошёлся с фактом за последний месяц.

---

## 3. Границы первой итерации

**Входит:** одно рабочее пространство, один редактор (пароль в env), read-only ссылка по токену, таймлайн, реестр проектов и карточки проектов, поиск свободного ресурса, закрытие недели со снимком, план/факт, экспорт, бэкапы, аудит.

**Не входит (итерации 2–3):** OAuth/SSO, несколько пространств в UI, ролевая модель, приглашения, публичная регистрация, интеграции с трекерами, мобильное редактирование, уведомления.

**Важно:** схема БД и слой доступа проектируются под мультиарендность **с первого дня** (см. §5). В первой итерации просто существует ровно одно пространство и один пользователь, но `workspace_id` есть во всех таблицах и во всех запросах. Ретрофит мультиарендности в работающую однопользовательскую схему — дорогая и болезненная операция, и её надо избежать заранее.

## 4. Функциональные требования

### 4.1 Таймлайн (главный экран)

Сетка: строки — сотрудники, колонки — календарные рабочие дни.

- Горизонт по умолчанию — **2 недели**, переключатели на 4 и 6 недель. Окно всегда начинается с понедельника текущей недели; можно листать назад и вперёд.
- Выходные и производственные праздники (справочник нерабочих дней на пространство) визуально приглушены и **не входят в ёмкость**.
- Каждый сотрудник — сворачиваемый блок:
  - **Свёрнутый вид (по умолчанию):** одна строка с суммарной загрузкой за день, окрашенная по уровню.
  - **Развёрнутый вид:** строки по проектам с долями дня плюс итоговая строка.
- Цветом кодируется **только уровень загрузки**, не проект. Проект читается текстом.
  - `0` — свободен, `0 < x < 1` — частично, `x = 1` — полная загрузка, `x > 1` — перегруз.
  - Отсутствие (отпуск, болезнь) — отдельная штриховка, ёмкость дня при этом равна нулю.
- Нижние итоговые строки, залипающие при скролле:
  - «Свободно, чел-дней» по каждому дню;
  - итог по каждой неделе;
  - процент утилизации команды за окно.
- Правая колонка на каждого: занято / свободно чел-дней за окно.
- Заголовок недели помечает **факт** (текущая и прошедшие) и **план** (будущие) — план отображается приглушённее.

### 4.2 Ввод и редактирование

Ввод должен быть быстрее, чем в таблице. Это главный критерий приёмки.

- **Клик по ячейке** — инлайн-редактор доли дня. Быстрые клавиши: `1` = 1.0, `5` = 0.5, `2` = 0.25, `7` = 0.75, `0` / `Delete` = очистить.
- **Навигация стрелками** между ячейками, `Tab` — вправо, `Enter` — вниз, как в таблице.
- **Протягивание (drag-fill)** по горизонтали — заполнить одинаковым значением диапазон дней.
- **Выделение прямоугольного диапазона** и ввод одного значения на всё выделение.
- **Копирование недели:** «продублировать неделю 1 в неделю 2» одной командой.
- **Добавление проекта сотруднику** — из строки поиска прямо в блоке сотрудника, без модалок и без вставки строк. Список проектов фильтруется по статусу: завершённые не предлагаются, но остаются в исторических данных.
- Все изменения — **оптимистичные**, с автосохранением и индикатором состояния сети. Никаких кнопок «Сохранить».
- **Undo/Redo** (`Cmd+Z` / `Cmd+Shift+Z`) на последние 50 действий в рамках сессии.
- Валидация: доля дня из набора `{0.25, 0.5, 0.75, 1.0}` плюс произвольное значение от 0 до 1 с шагом 0.05. Суммарная загрузка **выше 1 разрешается** и подсвечивается как перегруз — запрещать нельзя, перегруз надо видеть, а не прятать.

### 4.3 Поиск свободного ресурса (сценарий S2)

Отдельная панель «Хватит ли людей».

Вход: диапазон дат, требуемый объём в чел-днях, опционально — требуемые навыки/теги и минимальная доля дня на человека (например «не меньше 0.5, дробить сильнее бессмысленно»).

Выход:
- суммарная свободная ёмкость в диапазоне и вердикт «хватает / не хватает, дефицит N чел-дней»;
- список кандидатов, отсортированный по свободной ёмкости, с разбивкой по дням;
- предупреждения по каждому кандидату:
  - **`bus factor`** — сотрудник помечен единственным носителем экспертизы по активному проекту;
  - **фрагментация** — свободное время рассыпано по получасам и цельного блока нет;
  - **отпуск** внутри диапазона;
  - **план, а не факт** — если диапазон дальше двух недель, надёжность оценки ниже.

Эта панель — то, ради чего сервис существует. Она не должна прятаться в меню.

> **Продуктовое ограничение, которое надо явно отразить в UI.** Свободная ёмкость отвечает на вопрос «есть ли время», но не на «можно ли переключить». Формально свободный человек может быть единственным носителем ключевой экспертизы. Поэтому у связки «сотрудник × проект» есть флаг `is_sole_owner`, и кандидаты с ним всегда выводятся с предупреждением, а не молча.

### 4.4 Реестр проектов и карточка проекта

**Реестр** — таблица со всеми проектами: код, название, ответственный, RAG-статус (🟢/🟡/🔴), фаза, ближайшая веха с датой, «что изменилось за неделю», статус жизненного цикла (активен / приостановлен / завершён), текущее число занятых людей.

Сортировка и фильтры по статусу и ответственному. Завершённые скрыты по умолчанию.

**Карточка проекта** — две зоны, жёстко разделённые:

*Верх — живой статус (меняется еженедельно):* RAG-статус, фаза, ответственный, ближайшая веха, блокеры, апдейт недели, дата последнего обновления. Плюс лог апдейтов: новая запись сверху, дата проставляется автоматически.

*Низ — содержательная часть (меняется редко):* цель, задачи и вехи с ответственными и статусом, задачи вне скоупа с причиной отклонения, архитектура и артефакты, зависимости, риски с митигациями, лог решений, ссылки с указанием, к кому обращаться за доступом.

Дополнительно на карточке: **виджет загрузки проекта** — кто и сколько на нём занят в текущем окне, суммарно чел-дней. Это связывает реестр с таймлайном и является главным преимуществом перед двумя отдельными табличками.

Поля содержательной части — markdown с превью.

### 4.5 Скользящее окно и закрытие недели

Кнопка **«Закрыть неделю»** выполняет транзакционно:

1. Снимок закрываемой недели в `week_snapshot` (факт).
2. Сравнение с планом, который был зафиксирован для этой недели ранее, и запись расхождения.
3. Сдвиг окна на неделю вперёд; неделя N+1 становится текущей.
4. Фиксация плана на новую неделю N+2 в момент первого заполнения (снимок «план»).
5. Запись в аудит.

Операция **обратима** в течение 24 часов (кнопка «Откатить закрытие недели»).

Напоминание: если неделя не закрыта к вторнику, в шапке появляется ненавязчивый баннер.

### 4.6 План vs факт

Экран «Точность планирования»: за последние N недель — насколько план, зафиксированный за неделю до, совпал с фактом. Метрики: средняя абсолютная ошибка по сотруднику, доля недель, где «свободный» ресурс так и не был задействован, топ проектов, стабильно съедающих больше плана.

Это не отчётность ради отчётности — это единственный объективный способ откалибровать шкалу оценки загрузки.

### 4.7 Экспорт и шаринг

- Экспорт текущего окна в **XLSX** и **CSV** (формат, повторяющий текущую таблицу, — для тех, кто привык).
- Экспорт реестра проектов в XLSX.
- **Read-only ссылка** с токеном: `/s/{token}`. Открывает таймлайн и реестр в режиме чтения, без логина. Токен можно отозвать и перевыпустить. Опционально — срок жизни.
- Ссылка на конкретный вид сохраняет состояние: диапазон дат, фильтры, режим свёрнутости.

### 4.8 Аудит и надёжность ввода

- `audit_log` на все изменения аллокаций, проектов, сотрудников: кто, что, старое и новое значение, когда.
- История изменений видна на карточке проекта и в блоке сотрудника.
- Мягкое удаление (`deleted_at`) для сотрудников и проектов: ничего не пропадает физически.

## 5. Модель данных

PostgreSQL. Все таблицы содержат `workspace_id` с внешним ключом и индексом, даже в первой итерации.

```
workspace
  id uuid pk, slug text unique, name text, timezone text default 'Europe/Moscow',
  week_starts_on smallint default 1, default_horizon_weeks smallint default 2,
  created_at, updated_at

app_user                       -- в итерации 1 ровно одна запись
  id uuid pk, email text unique, name text, password_hash text,
  is_superuser bool, created_at, last_login_at

membership                     -- задел под ролёвку итерации 2
  id uuid pk, workspace_id fk, user_id fk,
  role text check (role in ('owner','editor','viewer')),
  created_at, unique(workspace_id, user_id)

member                         -- сотрудник
  id uuid pk, workspace_id fk, name text, role_title text,
  capacity_per_day numeric(3,2) default 1.00,
  tags text[],                 -- навыки: 'cuda','rag','infra'
  sort_order int, is_active bool default true,
  deleted_at timestamptz null, created_at, updated_at

project
  id uuid pk, workspace_id fk, code text, name text,
  lifecycle text check (lifecycle in ('active','paused','finished')) default 'active',
  rag_status text check (rag_status in ('green','amber','red')) default 'green',
  phase text, owner_member_id fk null,
  next_milestone text, next_milestone_date date,
  weekly_update text, goal text, scope_md text, out_of_scope_md text,
  architecture_md text, dependencies_md text, risks_md text,
  decisions_md text, links_md text,
  status_updated_at timestamptz,
  deleted_at timestamptz null, created_at, updated_at,
  unique(workspace_id, code) where deleted_at is null

project_update                 -- лог апдейтов на карточке
  id uuid pk, workspace_id fk, project_id fk,
  body text, rag_status_after text null,
  created_by fk, created_at

milestone
  id uuid pk, workspace_id fk, project_id fk, title text,
  due_date date, status text check (status in ('planned','in_progress','done','dropped')),
  owner_member_id fk null, sort_order int

allocation                     -- ядро системы
  id uuid pk, workspace_id fk, member_id fk, project_id fk,
  day date, load numeric(3,2) check (load > 0 and load <= 1),
  is_sole_owner bool default false, note text,
  created_by fk, created_at, updated_at,
  unique(workspace_id, member_id, project_id, day)

absence
  id uuid pk, workspace_id fk, member_id fk,
  date_from date, date_to date,
  kind text check (kind in ('vacation','sick','holiday','other')),
  note text, created_at

non_working_day                -- производственный календарь
  id uuid pk, workspace_id fk, day date, title text,
  unique(workspace_id, day)

week_snapshot
  id uuid pk, workspace_id fk, week_start date,
  kind text check (kind in ('plan','fact')),
  payload jsonb,               -- полный слепок аллокаций недели
  created_at, unique(workspace_id, week_start, kind)

share_link
  id uuid pk, workspace_id fk, token text unique,
  scope text default 'read',
  expires_at timestamptz null, revoked_at timestamptz null,
  created_at, last_accessed_at

audit_log
  id bigserial pk, workspace_id fk, actor_user_id fk null,
  entity_type text, entity_id uuid, action text,
  before jsonb, after jsonb, created_at
```

**Индексы:** `allocation (workspace_id, day)`, `allocation (workspace_id, member_id, day)`, `allocation (workspace_id, project_id, day)`, `audit_log (workspace_id, created_at desc)`.

**Инварианты, проверяемые на уровне БД и приложения:**

- Аллокация не может ссылаться на завершённый проект **при создании** (существующие остаются нетронутыми).
- Аллокация не создаётся на нерабочий день и на день, попадающий в отсутствие сотрудника; при попытке — понятная ошибка с предложением сначала снять отпуск.
- Сумма `load` по сотруднику за день **не ограничена сверху** — перегруз легален и отображается.
- Все запросы к данным проходят через слой, обязательно принимающий `workspace_id`. Ни один репозиторный метод не должен уметь работать без него.

## 6. API

REST, префикс `/api/v1`, JSON, аутентификация по httpOnly cookie-сессии; для read-only — по токену в пути.

```
POST   /auth/login                       {email, password} -> set-cookie
POST   /auth/logout
GET    /auth/me

GET    /timeline?from=&to=               агрегированный ответ для сетки:
                                         члены команды, их аллокации, отсутствия,
                                         нерабочие дни, посчитанные итоги по дням
POST   /allocations                      {member_id, project_id, day, load}
POST   /allocations/bulk                 массовое проставление по диапазону (drag-fill)
PATCH  /allocations/{id}                 {load, note, is_sole_owner}
DELETE /allocations/{id}
POST   /allocations/copy-week            {from_week_start, to_week_start, mode: replace|merge}

GET    /capacity/search                  ?from=&to=&needed_person_days=&min_daily=&tags=
                                         -> вердикт, кандидаты, предупреждения

GET    /members                          POST /members  PATCH /members/{id}  DELETE /members/{id}
POST   /members/reorder
GET    /absences                         POST /absences  DELETE /absences/{id}

GET    /projects                         ?lifecycle=&owner=
POST   /projects                         PATCH /projects/{id}   DELETE /projects/{id}
GET    /projects/{id}                    карточка целиком, включая вехи, апдейты и загрузку
POST   /projects/{id}/updates            добавить запись в лог апдейтов
GET    /projects/{id}/load?from=&to=     виджет загрузки проекта

POST   /weeks/close                      {week_start} -> снимок + сдвиг окна
POST   /weeks/close/undo                 {week_start}
GET    /weeks/accuracy?weeks=8           план vs факт

GET    /export/timeline.xlsx?from=&to=
GET    /export/projects.xlsx

POST   /share-links                      создать read-only ссылку
DELETE /share-links/{id}                 отозвать
GET    /s/{token}/timeline               публичный read-only срез
GET    /s/{token}/projects

GET    /admin/backups                    список бэкапов
POST   /admin/backups/run                бэкап по требованию
GET    /healthz                          liveness
GET    /readyz                           readiness (проверяет БД)
```

`GET /timeline` должен возвращать всё нужное для отрисовки **одним запросом** — N+1 в сетке недопустим. Ответ на две недели и девять человек должен укладываться в 200 мс на прогретой БД.

## 7. Архитектура и стек

**Бэкенд:** Python 3.12, FastAPI, SQLAlchemy 2.x (async), Alembic, Pydantic v2, `uv` для зависимостей.

**Фронтенд:** React 18 + TypeScript + Vite, TanStack Query для серверного состояния, Tailwind. Виртуализация строк для сетки не нужна при девяти сотрудниках, но компонент сетки должен быть написан так, чтобы её можно было добавить.

**Сетка — собственный компонент, не готовая библиотека таблиц.** Требования по клавиатуре, drag-fill и вложенным строкам плохо ложатся на generic-гриды, и борьба с чужими абстракциями обойдётся дороже своей реализации на CSS Grid.

**Сборка:** фронтенд собирается в статику, FastAPI отдаёт её как SPA-fallback. Один сервис на Railway вместо двух — меньше стоимости, меньше CORS, проще деплой.

**Миграции:** только Alembic, автоприменение в release-фазе после бэкапа (см. §9).

**Тайм-зона:** все даты аллокаций — `date` без времени, интерпретируются в таймзоне пространства. Никаких `timestamp` для дней планирования — это классический источник сдвига на сутки.

## 8. Деплой на Railway

Один Railway-проект, окружения `production` и `staging`.

**Сервисы:**

1. `web` — приложение. Dockerfile, multi-stage: сборка фронта на node, затем python-образ. Порт из `$PORT`. Healthcheck на `/healthz`.
2. `postgres` — managed Postgres от Railway.
3. `cron-backup` — сервис по расписанию, ежедневный бэкап (см. §9).
4. `cron-verify` — еженедельная проверка восстановимости бэкапа.

**Переменные окружения:**

```
DATABASE_URL                 (от Railway)
SECRET_KEY                   подпись сессий
ADMIN_EMAIL, ADMIN_PASSWORD  сид первого пользователя
APP_BASE_URL
WORKSPACE_SLUG=xops
TZ=Europe/Moscow
BACKUP_S3_ENDPOINT           S3-совместимое хранилище (Cloudflare R2 / Backblaze B2)
BACKUP_S3_BUCKET
BACKUP_S3_ACCESS_KEY / BACKUP_S3_SECRET_KEY
BACKUP_ENCRYPTION_KEY        age/gpg-ключ для шифрования дампов
BACKUP_RETENTION_DAILY=7 / WEEKLY=4 / MONTHLY=6
SENTRY_DSN                   опционально

```

**Release-фаза:** `alembic upgrade head` выполняется **только после** успешного pre-deploy бэкапа. Если бэкап не удался — деплой останавливается.

Требуется `railway.json` / `railway.toml` в репозитории, чтобы конфигурация была кодом, а не кликами в UI.

## 9. Бэкапы и восстановление

Это обязательная часть первой итерации, не «потом». Сервис хранит единственную копию планов команды; потеря данных означает потерю доверия к инструменту навсегда.

### 9.1 Что и куда

- **Ежедневный логический дамп** `pg_dump -Fc` в 03:00 по МСК.
- **Ежедневный человекочитаемый JSON-экспорт** пространства (сотрудники, проекты, аллокации, снимки) — независимый от версии PostgreSQL способ восстановления и одновременно формат для миграции на другой стек.
- Оба артефакта **шифруются** (`age`) и кладутся в S3-совместимое хранилище **вне Railway**. Бэкап в той же инфраструктуре, что и БД, — не бэкап.
- Имена: `tideline/{env}/{YYYY-MM-DD}/dump.pgc.age` и `.../export.json.age`.

### 9.2 Ротация

7 ежедневных, 4 еженедельных (воскресные), 6 ежемесячных (первое число). Удаление устаревших — тем же cron-сервисом, с логом того, что удалено.

### 9.3 Дополнительные точки бэкапа

- **Перед каждой миграцией** — автоматический дамп с меткой `pre-migration-{revision}`.
- **Перед закрытием недели** — снимок в `week_snapshot` (это логический бэкап уровня приложения, не заменяет физический).

### 9.4 Проверка восстановимости

Еженедельная задача: поднять временную БД, восстановить последний дамп, выполнить набор проверок (число сотрудников, число аллокаций за последний месяц, сумма `load` за прошлую неделю совпадает с ожидаемой), затем удалить временную БД. Результат — в лог и в `/admin/backups`.

**Непроверенный бэкап следует считать отсутствующим.** Эта задача не опциональна.

### 9.5 Восстановление

- Документированная процедура в `docs/RESTORE.md` с точными командами.
- `make restore FILE=...` — скрипт, который расшифровывает, восстанавливает в указанную БД и выводит сводку.
- В `/admin/backups` — список артефактов с размером, датой, статусом верификации и кнопкой скачивания.
- **Целевые показатели:** RPO ≤ 24 часа, RTO ≤ 1 час.
- Раздел в README: «Что делать, если всё упало» — по шагам, для человека в стрессе.

## 10. Наблюдаемость и эксплуатация

- Структурные логи в JSON, с `request_id` и `workspace_id`.
- Метрики на `/metrics` (Prometheus-формат): latency по эндпоинтам, число аллокаций, статус последнего бэкапа.
- Sentry для исключений, если задан DSN.
- `/healthz` — процесс жив; `/readyz` — БД отвечает и миграции применены.
- Отдельная метрика `backup_last_success_timestamp` — по ней можно поставить алерт «бэкапа не было больше 30 часов».

## 11. Безопасность

- Пароли — `argon2`. Сессии — httpOnly + Secure + SameSite=Lax cookie.
- Rate limiting на `/auth/login` и на публичные `/s/{token}/*`.
- Токены ссылок — не менее 32 байт энтропии, хранятся хешированными, при отзыве становятся невалидны немедленно.
- Публичный режим отдаёт **только** нужные поля: имена, проекты и загрузку; никаких заметок, логов аудита и внутренних ссылок. Это должно обеспечиваться отдельными сериализаторами, а не флагом в общем.
- CSP, HSTS, отключённый `X-Powered-By`.
- Никаких секретов в репозитории; `.env.example` с описанием переменных.

## 12. Требования к интерфейсу

- **Плотность прежде красоты.** Две недели на девять человек должны помещаться на ноутбучном экране без горизонтального скролла.
- Палитра уровней загрузки — приглушённая, различимая при дальтонизме (не только красный/зелёный: перегруз дополнительно маркируется диагональной штриховкой или значком).
- Первая колонка с именами закрепляется **только** при горизонтальном скролле, то есть при горизонте больше двух недель. На двухнедельном горизонте закрепление не нужно.
- Тёмная тема — по системной настройке.
- Мобильный режим — только чтение, вертикальный список по сотрудникам. Редактировать сетку с телефона никто не будет, и притворяться не надо.
- Пустые состояния объясняют, что делать дальше, а не просто говорят «нет данных».
- Все действия достижимы с клавиатуры; `?` открывает список горячих клавиш.

## 13. Приёмка

Итерация считается готовой, когда выполняется всё:

1. Загрузка команды из 7 человек на две недели проставляется с нуля меньше чем за 2 минуты, только с клавиатуры.
2. Панель поиска ресурса на запрос «15 чел-дней с 3 по 14 августа» отвечает вердиктом и списком кандидатов с предупреждениями.
3. Закрытие недели создаёт снимок, сдвигает окно и откатывается кнопкой.
4. Экран точности планирования показывает расхождение план/факт минимум за 4 недели демо-данных.
5. Read-only ссылка открывается в инкогнито, показывает таймлайн и не даёт ничего изменить; после отзыва возвращает 404.
6. Экспорт в XLSX открывается в Google Sheets без ошибок.
7. Бэкап выполняется по расписанию, шифруется, попадает в бакет, ротируется; еженедельная верификация восстанавливает дамп и проходит проверки.
8. `make restore` восстанавливает вчерашний дамп в чистую БД, приложение поднимается на нём и показывает те же данные.
9. Развёрнуто на Railway из репозитория, миграции применяются автоматически, деплой падает, если pre-deploy бэкап не удался.
10. `pytest` зелёный, покрытие бизнес-логики (расчёт ёмкости, поиск ресурса, закрытие недели) не ниже 80%.

## 14. Тесты

- **Юнит:** расчёт свободной ёмкости с учётом отпусков, праздников, частичной ставки; ранжирование кандидатов; логика закрытия недели и отката.
- **Интеграционные:** API поверх реальной БД в контейнере, включая изоляцию по `workspace_id` — тест, который проверяет, что запрос с чужим `workspace_id` не возвращает данные. Написать его сейчас, пока пространство одно, а не когда их станет много.
- **E2E (Playwright):** сценарии S1–S4.
- **Тест бэкапа:** дамп → восстановление → сверка контрольных сумм по ключевым таблицам.

## 18. Явные не-цели

Чтобы Claude Code не пытался это построить:

- Это **не таск-трекер**. Задач нет, есть только доли дня на проектах. Никаких статусов задач, досок и зависимостей.
- Это **не гант с критическим путём**. Зависимости между проектами не моделируются.
- Это **не таймшит**. Фактически отработанные часы не собираются и собираться не будут — это провоцирует имитацию занятости и убивает доверие к инструменту.
- Это **не система учёта отпусков**. Отпуска нужны только чтобы корректно вычитать ёмкость.
- Горизонт планирования сознательно короткий. Квартальное ресурсное планирование — отдельный класс задач, и смешивать их не нужно.
